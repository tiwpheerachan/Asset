# ระบบขออนุมัติภายใน (Internal Approval)

ระบบยื่นและอนุมัติคำขอภายในองค์กร แนวเดียวกับระบบอนุมัติของ Lark/Feishu —
**ผู้ดูแลสร้างฟอร์มเองได้** พร้อมสายอนุมัติของแต่ละฟอร์ม (เรียงขั้น / ขนาน / สำเนาถึง)
ประวัติการดำเนินการครบทุกขั้น และพิมพ์เป็น PDF ได้

รองรับ **3 ภาษา: ไทย / English / 中文** และมีโหมดสว่าง–มืด

**เทคโนโลยี:** Next.js 15 (App Router) · React 19 · TypeScript · Tailwind CSS · PostgreSQL (node-postgres)
ไม่ต้องติดตั้ง database server แยก — ข้อมูลทั้งหมดอยู่ในโฟลเดอร์ `data/`

---

## เริ่มใช้งาน

```bash
npm install
```

```bash
npm run seed
```

```bash
npm run dev
```

เปิด http://localhost:3000

> **ก่อนเปิดใช้จริงต้องรัน `npm run reset-passwords`** — ตอนนี้ทุกบัญชีใช้รหัสเดียวกัน
> ซึ่งเหมาะกับช่วงทดลองเท่านั้น เพราะรหัสที่ทุกคนรู้เท่ากับไม่มีรหัส
> และประวัติการอนุมัติจะพิสูจน์ไม่ได้ว่าใครเป็นคนกดจริง
>
> คำสั่งนั้นจะสุ่มรหัสให้ทุกคนคนละอัน เขียนลงไฟล์ `data/initial-passwords.txt` (สิทธิ์ 600)
> ส่งให้เจ้าของบัญชีแล้วลบไฟล์ทิ้ง

### บัญชีตัวอย่าง (รหัสผ่าน `password123` ทุกบัญชี)

| อีเมล | ชื่อ | ตำแหน่ง | สิทธิ์ |
|---|---|---|---|
| `admin@company.co.th` | ผู้ดูแลระบบ | IT Administrator | ผู้ดูแลระบบ |
| `sales1@company.co.th` | สมชาย ใจดี | ผู้แทนขาย (ฝ่ายขาย) | ผู้ใช้ทั่วไป |
| `sales2@company.co.th` | ปรียา วงศ์ทอง | ผู้แทนขาย (ฝ่ายขาย) | ผู้ใช้ทั่วไป |
| `manager@company.co.th` | วิชัย รุ่งเรือง | ผู้จัดการแผนก (ฝ่ายขาย) | **หัวหน้าทีม** |
| `finance@company.co.th` | อรทัย ศรีสุข | ผู้จัดการฝ่ายบัญชี | **หัวหน้าทีม** |
| `md@company.co.th` | ธนกร พาณิชย์ | กรรมการผู้จัดการ | ผู้ใช้ทั่วไป |
| `purchase@company.co.th` | กิตติ มั่นคง | หัวหน้าฝ่ายจัดซื้อ | **หัวหน้าทีม** |

> **ก่อนใช้งานจริง** ให้เข้าด้วยบัญชี admin แล้ว
> 1. เมนู **แผนก** — สร้างแผนกให้ตรงกับโครงสร้างองค์กรจริง
> 2. เมนู **ผู้ใช้งาน** — เปลี่ยนรหัสผ่านทุกบัญชี ลบบัญชีตัวอย่างที่ไม่ใช้ แล้วตั้งค่าให้ครบ 3 อย่าง:
>    **แผนก** (กำหนดว่าใครเห็นเอกสารของใคร) · **ตำแหน่งงาน** (สายอนุมัติอ้างตำแหน่งนี้
>    ถ้าไม่กำหนดจะส่งอนุมัติไม่ได้) · **สิทธิ์** (ตั้งหัวหน้าทีมให้แต่ละแผนก)
> 3. เมนู **สายอนุมัติ** — แก้วงเงินและผู้อนุมัติให้ตรงกับอำนาจอนุมัติจริงขององค์กร
>    **ค่าที่ให้มาเป็นค่าตัวอย่าง ไม่ใช่ของจริง**

## ความสามารถ

- **หน้าแรกเป็นกริดการ์ดฟอร์ม** แยกหมวดและค้นหาได้ แต่ละฟอร์มมีไอคอนและสีของตัวเอง
- **สร้างฟอร์มเองได้แบบ Google Form** — ฟิลด์เป็นการ์ดเรียงกัน คลิกแก้ตรงนั้น
  ลากสลับลำดับ ทำสำเนา ลบ ได้ในที่เดียว · รหัสฟิลด์ตั้งให้อัตโนมัติจากชื่อ (แก้เองได้ในตั้งค่าขั้นสูง)
  ที่ `/admin/forms`
  รองรับ 11 ชนิด: ข้อความ · ข้อความหลายบรรทัด · ตัวเลข · จำนวนเงิน · วันที่ ·
  ตัวเลือกเดี่ยว/หลายข้อ · เลือกบุคคล · ไฟล์แนบ · รูปภาพ · **ตารางรายการ** (เพิ่มแถวได้ พร้อมผลรวมอัตโนมัติ)
  มาพร้อมแม่แบบตั้งต้น 7 ใบ จัดกลุ่มเป็นหมวดและค้นหาได้ที่หน้า “ส่งคำขอ”
- **สายอนุมัติต่อฟอร์ม** — แต่ละแม่แบบมีขั้นตอนของตัวเอง แต่ละขั้นเลือกได้ว่าเป็น
  **ต้องอนุมัติ** หรือ **สำเนาถึง (抄送)** และถ้ามีหลายคนในขั้นเดียวกันเลือกได้ว่า
  **ใครก็ได้ 1 คน** หรือ **ต้องครบทุกคน**
- **เงื่อนไขตามค่าในฟอร์ม** — ตั้งได้ว่าขั้นไหนทำงานเมื่อไร เช่น “ให้ MD อนุมัติเมื่อวงเงิน ≥ 500,000”
  **ผู้จัดทำเลือกผู้อนุมัติเองไม่ได้** (ปิดช่องโหว่การเลือกคนที่อนุมัติง่ายที่สุด)
  กติกาอ้าง *ตำแหน่งงาน* ไม่ใช่ตัวบุคคล จึงเปลี่ยนคนในตำแหน่งได้โดยไม่ต้องแก้กติกา
- **ระหว่างพิจารณาทำได้มากกว่าอนุมัติ/ไม่อนุมัติ** — **ส่งกลับให้แก้** (เอกสารไม่ถูกปิด แก้แล้วส่งใหม่ได้) ·
  **ถ่ายโอน** ให้คนอื่นพิจารณาแทน · **แทรกผู้อนุมัติ** เพิ่มกลางคัน (ก่อนหรือหลังตัวเอง)
- **สำเนาถึงพร้อมสถานะอ่านแล้ว** — ขั้นสำเนาไม่บล็อกเอกสาร ระบบแจ้งแล้วเดินต่อทันที
  และบันทึกว่าใครเปิดอ่านเมื่อไหร่
- **ความคิดเห็น** แยกจากความเห็นตอนอนุมัติ — คุยกันในเอกสารได้ทุกคนที่เห็นเอกสาร
- **3 ภาษา (ไทย / English / 中文)** — สลับได้จากปุ่มมุมขวาบน จำค่าไว้ใน cookie
  วันที่และตัวเลขปรับตามภาษาด้วย (ไทยใช้ปีพุทธศักราช · จีนใช้รูปแบบ 2026年8月17日)
  **ข้อความที่ผู้ใช้กรอกเองไม่ถูกแปล** — ชื่อแม่แบบ ชื่อฟิลด์ ชื่อแผนก และเนื้อหาคำขอ
  แสดงตามที่บันทึกไว้ (เหมือน Lark ที่ฟอร์มภาษาจีนก็ขึ้นภาษาจีน)
- **โหมดสว่าง / มืด** ทั้งระบบ จำค่าที่เลือกไว้
- **แจ้งเตือนและกดอนุมัติผ่าน Lark / Feishu** — ส่งการ์ดเข้าแชทเมื่อถึงคิว
  กดปุ่ม “อนุมัติ / ไม่อนุมัติ” ได้ในแชทเลย ไม่ต้องเปิดเว็บ
  ผลที่กดจากแชทกับจากเว็บใช้ตรรกะเดียวกันทุกประการ (ดูหัวข้อถัดไป)
- **อนุมัติ 2 ระดับ** — *อนุมัติเบื้องต้น* (ยังไม่ก่อภาระค่าใช้จ่าย → เริ่มงานได้)
  แล้วจึง *อนุมัติจริง* เมื่อทราบค่าใช้จ่ายจริง
  ประเภทที่ตั้งกติกาขั้นเบื้องต้นไว้จะต้องผ่านขั้นนี้ก่อนเสมอ
- **ไม่อนุมัติ** ปิดเอกสารทันทีและต้องระบุเหตุผล
- **ดึงกลับมาแก้ไข** — ผู้จัดทำดึงเอกสารกลับได้หากยังไม่มีใครพิจารณา (admin ดึงกลับได้เสมอ)
- **นับเวลาที่ค้าง** — เห็นว่าเอกสารค้างที่ขั้นไหนมากี่วัน ทั้งในรายการและในบันทึกการอนุมัติ
- **เลขที่เอกสารอัตโนมัติ** รูปแบบ `AP-{ตัวย่อฟอร์ม}-{ปีเดือน}-{ลำดับ 4 หลัก}` เช่น `AP-MARK-202608-0007`
  ลำดับเดินแยกของใครของมันต่อฟอร์มต่อเดือน · ตัวย่อตั้งเองได้ที่หน้าตั้งค่าแม่แบบ (ไม่ตั้งก็ย่อจากรหัสให้ 4 ตัว)
  ออกแบบให้**พิมพ์ลงช่องอ้างอิงในระบบ OA แล้วคนอ่านรู้ว่าเป็นเอกสารอะไร เดือนไหน**
  มีปุ่มคัดลอกในหน้าเอกสาร · เอกสารที่ออกก่อนเปลี่ยนรูปแบบยังคงเลขเดิม (`YYYYMMDD` + ลำดับของวัน) ไว้ทั้งหมด
- **ไฟล์แนบ** ไฟล์ละไม่เกิน 10 MB เข้าถึงได้เฉพาะผู้ที่เกี่ยวข้องกับเอกสาร
- **พิมพ์ / บันทึกเป็น PDF** หน้าเอกสารขนาด A4 จัดวางตามฟอร์ม Excel เดิม
  ตั้งได้รายฟอร์มว่าจะมีช่องลายเซ็นหรือไม่ — **ไม่ต้องมี** (แสดงตารางบันทึกการอนุมัติแทน สำหรับเอกสารภายใน) ·
  **ไม่บังคับ** (ค่าเริ่มต้น) · **ต้องมีครบ** (เอกสารที่ออกให้ลูกค้า เตือนก่อนพิมพ์ถ้าลายเซ็นใครขาด)
- **ประวัติการดำเนินการ** บันทึกทุกการกระทำพร้อมผู้ทำ เวลา และ**มูลค่า ณ ขณะนั้น**
  จึงย้อนดูได้ว่าใครอนุมัติที่ราคาเท่าไหร่ แม้มูลค่าจะถูกแก้ภายหลัง
- **สิทธิ์การเข้าถึงแยกตามทีม** — 3 ระดับ
  | สิทธิ์ | เห็นอะไร |
  |---|---|
  | ผู้ใช้ทั่วไป | เฉพาะเอกสารที่ตนจัดทำ หรือที่ตนอยู่ในสายอนุมัติ |
  | หัวหน้าทีม | ของตัวเอง + ที่อยู่ในสายอนุมัติ + **ทุกฉบับที่คนในแผนกตนเป็นผู้จัดทำ** (มีแท็บ “ทีมของฉัน”) |
  | ผู้ดูแลระบบ | ทั้งหมด |
- **มอบหมายให้อนุมัติแทนช่วงลา** — ตั้งช่วงวันที่แล้วให้คนที่ระบุกดแทนได้
  **ไม่ย้ายเจ้าของงาน** แถวยังเป็นชื่อคนเดิม พ้นช่วงแล้วกลับมาเป็นของเขาเองโดยไม่ต้องย้ายข้อมูลกลับ
  ระบบบันทึกว่าใครกดจริง และ**กันไม่ให้ใช้สิทธิ์แทนมาอนุมัติเอกสารของตัวเอง**
  สิทธิ์ไม่ต่อทอด (ก→ข, ข→ค ไม่ทำให้ ค แทน ก ได้) · ตั้งเองที่ `/profile` หรือให้แอดมินตั้งที่ `/admin/delegations`
- **เตือนงานค้างอัตโนมัติ** — ค้างเกิน 3 วันทวงผู้อนุมัติ (การ์ดมีปุ่มอนุมัติในตัว)
  เกิน 7 วันแจ้งหัวหน้าแผนกและผู้ยื่นด้วย
  นับเวลาจาก**ตอนที่งานตกถึงมือคนนั้น** ไม่ใช่ตอนยื่น — คนขั้นสองจึงไม่โดนทวงเพราะขั้นแรกดองไว้
  ส่งเฉพาะเวลาทำการ ข้ามเสาร์อาทิตย์ และเตือนคนเดิมเรื่องเดิมได้วันละครั้ง · ดูที่ `/admin/reminders`
- **หน้าวิเคราะห์ประสิทธิภาพ** ที่ `/admin/analytics` — ใครเป็นคอขวด (เฉลี่ยต่อขั้น เฉพาะช่วงที่งานอยู่ในมือเขาจริง)
  อายุงานที่ค้างอยู่ · ปริมาณรายสัปดาห์ · แยกตามประเภทเอกสาร · เวลาปิดงานทั้งค่ากลางและค่าเฉลี่ย
- **ออกเอกสารจากคำขอที่อนุมัติแล้ว** — ใบแจ้งหนี้ / ใบลดหนี้ (CN) / ใบเพิ่มหนี้ (DN) / ใบเสร็จ
  **เลขที่เดินแยกชุดตามประเภทและรีเซ็ตรายเดือน** (`INV-202608-0001`) ออกได้เฉพาะเรื่องที่อนุมัติครบแล้ว
  ยกเลิกได้แต่ไม่ลบทิ้ง เลขจึงไม่ขาดช่วง
- **ลายเซ็นจริงบนเอกสารพิมพ์** — อัปโหลดที่ `/profile` แสดงเฉพาะขั้นที่กดอนุมัติแล้ว
  ถ้ามีคนอนุมัติแทน จะใช้ลายเซ็นของ**คนที่กดจริง** พร้อมวงเล็บบอกชื่อ
- **เชื่อมระบบภายนอก (ERP / บัญชี)** ที่ `/admin/erp` — ยิง webhook ออกเมื่ออนุมัติ/ปฏิเสธ/ออกเอกสาร
  (ลงลายมือชื่อ HMAC-SHA256 ให้ปลายทางตรวจได้ · ลองซ้ำอัตโนมัติเมื่อปลายทางล่ม)
  และเปิด REST API ให้ระบบที่รับ push ไม่ได้มาดึงเองที่ `/api/v1/requests`
- **สำรองข้อมูลอัตโนมัติ** ที่ `/admin/backup` — เขียนออกเป็นไฟล์ `.sql` ที่กู้คืนด้วย `psql` ได้ และอ่านตรวจด้วยตาได้
  **ตรวจสำเนาทุกครั้งหลังสร้าง** ถ้าเปิดไม่ออกหรือข้อมูลไม่ครบจะลบทิ้งแล้วบันทึกว่าล้มเหลว
  ไฟล์แนบสำรองแบบเพิ่มเฉพาะของใหม่ · ดาวน์โหลดเก็บนอกเครื่องได้
- **กันการเดารหัสผ่าน** — นับทั้งต่อบัญชีและต่อ IP (กันไล่ยิงรหัสเดียวใส่หลายบัญชี)
  เข้าสำเร็จล้างประวัติให้ · ผู้ดูแลปลดล็อกก่อนครบเวลาได้
- **ส่งออก CSV** ตามตัวกรองที่เลือกอยู่ ผ่านสิทธิ์การมองเห็นชุดเดียวกัน (มี BOM ให้ Excel อ่านภาษาไทยได้)
- **ค้นหาและแบ่งหน้าที่ฐานข้อมูล** — ไม่โหลดทั้งตารางขึ้นมากรองในหน่วยความจำ
- **แผนกเป็นตารางจริง** ไม่ใช่ข้อความอิสระ — ใช้ทั้งแบ่งสิทธิ์และหาผู้อนุมัติในแผนกเดียวกับผู้จัดทำ

## สถานะเอกสาร

| สถานะ | ความหมาย |
|---|---|
| `DRAFT` | ฉบับร่าง — แก้ไขได้ ยังไม่เข้าสายอนุมัติ |
| `PENDING` | รออนุมัติ — อยู่ที่ขั้น `current_step` ของระดับ `stage` |
| `RETURNED` | ถูกส่งกลับให้ผู้จัดทำแก้ — แก้แล้วส่งใหม่ได้ ประวัติเดิมยังอยู่ |
| `PRELIM_APPROVED` | ผ่านอนุมัติเบื้องต้นครบแล้ว — เริ่มงานได้ รอผู้จัดทำยื่นอนุมัติจริง |
| `APPROVED` | ผ่านอนุมัติจริงครบทุกขั้นแล้ว |
| `REJECTED` | มีผู้ไม่อนุมัติ เอกสารปิด |
| `CANCELLED` | ผู้จัดทำยกเลิก |

### เส้นทางของเอกสาร

```
DRAFT ─ส่ง─→ PENDING (stage=PRELIM) ─ครบทุกขั้น─→ PRELIM_APPROVED
                                                        │ ผู้จัดทำยืนยันมูลค่าจริง
                                                        ↓
                              PENDING (stage=FINAL) ─ครบทุกขั้น─→ APPROVED

ประเภทที่ไม่มีกติกาขั้นเบื้องต้น: DRAFT ─ส่ง─→ PENDING (stage=FINAL) ─→ APPROVED
ไม่อนุมัติได้ทุกขั้น → REJECTED · ผู้จัดทำยกเลิกได้ก่อนอนุมัติ → CANCELLED
```

> วงเงินที่ยืนยันตอนยื่นอนุมัติจริงเป็นตัวคำนวณสายอนุมัติของขั้นจริงใหม่ —
> ถ้ามูลค่าจริงข้ามช่วงวงเงิน ระบบจะเพิ่มผู้อนุมัติระดับสูงขึ้นให้เอง

## เชื่อมกับระบบกลาง Central Login (SSO)

ระบบนี้ต่อกับ Central Login ด้วย **OpenID Connect** (Authorization Code + PKCE, ตรวจลายเซ็น RS256 ผ่าน JWKS)

**หลักที่ยึด: ระบบกลางเป็นเจ้าของตัวตนและสิทธิ์ — แอปนี้ไม่กำหนดสิทธิ์เอง**

| สิ่งที่มาจากระบบกลาง | สิ่งที่ยังตั้งในแอปนี้ |
|---|---|
| ตัวตน (sub) · ชื่อ · อีเมล | **ตำแหน่งงาน** (SALES_MANAGER, MD, …) |
| **สิทธิ์** (ผู้ดูแลระบบ / หัวหน้าทีม / ผู้ใช้ทั่วไป) จาก claim `roles` | แม่แบบฟอร์มและสายอนุมัติ |
| แผนก จาก claim `groups` (ถ้าชื่อตรงกับแผนกที่มีอยู่) | |

> ทำไม "ตำแหน่งงาน" ไม่ไปอยู่ที่ระบบกลาง — เพราะมันไม่ใช่สิทธิ์การเข้าถึง แต่เป็นกติกาว่า
> เอกสารต้องวิ่งไปหาใคร ซึ่งเป็นเรื่องภายในกระบวนการอนุมัติ

### ขั้นตอนตั้งค่า
1. ที่ Central Login → **แอปทั้งหมด** → เปิดแอป **Internal Approval** → **จัดการ / API key**
2. ตั้ง **รูปแบบสิทธิ์** เป็น **ระบบกลางคุม** และ **เปิดใช้ SSO**
3. ใส่ **Redirect URI**: `https://<โดเมนของระบบ>/api/auth/sso/callback`
4. คัดลอก Client ID / Client Secret มาใส่ `.env.local` (ดู `.env.example`)
5. เข้าเมนู **ระบบกลาง (SSO)** ในแอปเพื่อตรวจว่าค่าครบและดูว่า role ที่ส่งมาจริงคืออะไร
6. ปรับ `SSO_ROLE_MAP` ให้ตรงกับชื่อ role ที่ระบบกลางส่งมา

> **เปิด `SSO_ALLOW_LOCAL_LOGIN=true` ไว้ตอนแรก** จนกว่าจะยืนยันว่าล็อกอินผ่านระบบกลางได้และ
> ได้สิทธิ์ผู้ดูแลจริง ไม่งั้นถ้า role map ผิดจะไม่มีใครเข้าหน้าผู้ดูแลได้เลย

### ที่ระบบทำให้อัตโนมัติ
- **เข้าครั้งแรกสร้างบัญชีให้เอง** ไม่ต้องเพิ่มผู้ใช้ล่วงหน้า
- ถ้าเคยมีบัญชีในแอปที่อีเมลตรงกัน จะผูกเข้าด้วยกันแทนการสร้างซ้ำ
- **สิทธิ์ถูกเขียนทับทุกครั้งที่ล็อกอิน** ตามที่ระบบกลางส่งมา — ช่องสิทธิ์ในหน้าผู้ใช้จึงถูกล็อก
- ออกจากระบบจะออกจากระบบกลางด้วย

## เชื่อมกับ Lark / Feishu

### สิ่งที่ระบบทำให้
| เหตุการณ์ | ใครได้รับ | การ์ดมีอะไร |
|---|---|---|
| ถึงคิวอนุมัติ | ผู้อนุมัติขั้นนั้น | รายละเอียดคำขอ + ปุ่ม **อนุมัติ / ไม่อนุมัติ / เปิดในระบบ** |
| ขั้นสำเนาถึง (抄送) | ผู้รับสำเนา | รายละเอียดคำขอ (ไม่มีปุ่มตัดสิน) |
| อนุมัติครบ / ไม่อนุมัติ / ถูกส่งกลับ | ผู้จัดทำ | สถานะล่าสุดพร้อมเหตุผล |
| ถ่ายโอน / แทรกผู้อนุมัติ | ผู้รับงานคนใหม่ | การ์ดขออนุมัติ |

กดอนุมัติจากแชทแล้ว ปุ่มบนการ์ดของคนอื่นในขั้นเดียวกันจะถูกปิดให้อัตโนมัติ
(สำคัญกับขั้นแบบ “ใครก็ได้ 1 คน”)

### ขั้นตอนตั้งค่า
1. สร้าง **Custom App** ที่ Developer Console
   (Lark สากล `open.larksuite.com` · Feishu จีน `open.feishu.cn` — คนละคลาวด์ ต้องเลือกให้ตรง)
2. เปิดสิทธิ์ (Permissions) อย่างน้อย: `im:message`, `im:message:send_as_bot`, `contact:user.base:readonly`
   — ตัวสุดท้ายใช้ค้นหาบัญชี Lark จากอีเมลของผู้ใช้
3. คัดลอก App ID / App Secret / Verification Token (หรือ Encrypt Key) มาใส่ `.env.local`
4. ใส่ **Request URL** ในหน้า **Event Subscription** และ **Message Card** ให้ชี้มาที่
   `https://<โดเมนของระบบ>/api/lark/callback`
5. เปิดเมนู **การเชื่อมต่อ** ในระบบ กด **ค้นหา Lark ID จากอีเมล** แล้วกด **ทดสอบการเชื่อมต่อ**

> **Request URL ต้องเข้าถึงได้จากอินเทอร์เน็ต** — Lark ยิง callback มาจากคลาวด์ ไม่ใช่จากเครื่องผู้ใช้
> ตอนพัฒนาบนเครื่องตัวเองให้ใช้ tunnel (เช่น `cloudflared` / `ngrok`) แล้วตั้ง `APP_BASE_URL` ตามนั้น

### ข้อจำกัดที่ตั้งใจไว้
- **กด “ไม่อนุมัติ” จากการ์ดจะใส่เหตุผลมาตรฐานให้** เพราะปุ่มบนการ์ดไม่มีช่องพิมพ์
  ถ้าต้องการเขียนเหตุผลเอง ให้กด “เปิดในระบบ” แล้วทำจากหน้าเว็บ
- **ถ้ายังไม่ตั้งค่า Lark ระบบทำงานได้ปกติทุกอย่าง** แค่ไม่มีการแจ้งเตือน —
  คิวจะถูกทำเครื่องหมาย `SKIPPED` พร้อมเหตุผล ดูได้ที่เมนูการเชื่อมต่อ
- **Lark ล่มไม่ทำให้อนุมัติไม่ได้** — ข้อความเข้าคิวในตาราง `notifications` ก่อนเสมอ
  ส่งไม่ผ่านจะลองใหม่ได้ 3 ครั้ง และกดส่งซ้ำเองได้จากหน้าการเชื่อมต่อ

## นำขึ้นใช้งานจริง

รันบนเครื่องภายในบริษัทหรือ VM ที่มี disk ถาวร:

```bash
npm run build && npm run start
```

ข้อควรทราบ:

- **ต้องรันจากโฟลเดอร์โปรเจกต์** เพราะ `src/lib/schema.sql` และ `src/lib/default-rules.json`
  ถูกอ่านด้วย path จาก `process.cwd()`
- **ฐานข้อมูลเดิมอัปเกรดอัตโนมัติ** ตอนเปิดแอปครั้งแรกหลังอัปเดตโค้ด — **สำรอง `data/` ก่อนอัปเดตทุกครั้ง**
  - เฟส 1: เพิ่มประเภทคำขอ / ระดับอนุมัติ / ตารางสายอนุมัติ
  - เฟส 2: ย้ายแผนกจากข้อความอิสระไปเป็นตาราง `departments` และเพิ่มสิทธิ์หัวหน้าทีม
  - เฟส 3: ย้ายจากระบบ memo 7 ประเภทตายตัว ไปเป็นแม่แบบฟอร์ม (`memos` → `requests`)
    เอกสารเดิมถูกแปลงเป็นคำขอของแม่แบบตามประเภทเดิม ค่าฟิลด์เก็บลง `requests.data` เป็น JSON
    **กติกาวงเงินเดิมถูกแปลงเป็นเงื่อนไข “ตั้งแต่วงเงิน X ขึ้นไป”** โดยใช้วงเงินต่ำสุดที่ผู้อนุมัติคนนั้นปรากฏ
    ซึ่งตรงกับตารางแบบสะสม — ควรตรวจซ้ำที่ `/admin/forms` หลังอัปเกรด
  - การอัปเกรด**ไม่เลื่อนสิทธิ์ใครเป็นหัวหน้าทีมให้อัตโนมัติ** ต้องตั้งเองที่เมนูผู้ใช้งาน
- **ไฟล์แนบเก็บบนดิสก์** (ไม่ได้อยู่ในฐานข้อมูล) จึงยังต้องมีดิสก์ถาวร — ถ้าจะขึ้น serverless ต้องย้ายไฟล์แนบไป object storage ก่อน
  หากต้องขึ้น Vercel ให้เปลี่ยนไปใช้ Postgres และย้ายไฟล์แนบไปเก็บบน object storage
- **สำรองข้อมูล** ด้วยการคัดลอกทั้งโฟลเดอร์ `data/`
- ตั้ง reverse proxy ให้เป็น **HTTPS** — cookie จะตั้ง flag `secure` อัตโนมัติเมื่อ `NODE_ENV=production`

## สิ่งที่ยังไม่มี

- **แชทกลุ่มของเอกสาร** แบบ Lark (ผูกกับระบบแชทองค์กร)
- แปลข้อมูลที่ผู้ใช้กรอกเอง (ชื่อฟอร์ม/ฟิลด์หลายภาษา) — ตอนนี้แสดงตามภาษาที่พิมพ์ไว้เท่านั้น
- **ส่งกลับไปยังขั้นกลางทาง** — ตอนนี้ส่งกลับได้ถึงผู้จัดทำเท่านั้น
