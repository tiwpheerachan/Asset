## 1. สรุปหนึ่งหน้าสำหรับคนทำ OneBook

**หน้าที่ของแต่ละระบบ**

- **Internal-Approve** คือที่ที่ *คำขอเกิดและถูกอนุมัติ* — พนักงานกรอกฟอร์ม ผู้มีอำนาจกดอนุมัติตามลำดับขั้น
- **OneBook** คือที่ที่ *เงินถูกบันทึกและจ่ายจริง* — ตั้งเจ้าหนี้ ออกเอกสาร ลงบัญชี ตัดจ่าย

**จุดเชื่อมหลักมีจุดเดียว:** เมื่อคำขอ **อนุมัติครบทุกขั้น** ระบบเราจะส่งข้อมูลใบนั้นไปให้ OneBook ทันที
เพื่อให้ฝ่ายบัญชีรับรู้และทำเอกสารต่อ โดยไม่ต้องมีใครเดินเอกสารหรือคีย์ซ้ำ

**สิ่งที่ต้องทำฝั่ง OneBook อย่างน้อยที่สุด**

1. เปิด endpoint หนึ่งตัวรับ `POST` จากเรา (เช่น `https://onebook.example/hooks/internal-approve`)
2. ตรวจลายมือชื่อที่ header `X-Signature-256` ด้วยกุญแจลับที่ตกลงกัน
3. ตอบ HTTP `2xx` ภายใน 15 วินาที (รับเข้าคิวก่อน แล้วค่อยประมวลผลทีหลัง)
4. กันการทำซ้ำ — เราอาจส่งใบเดิมซ้ำได้ ให้ยึด `request.doc_no` + `event` เป็นตัวกันซ้ำ

**สิ่งที่เราให้ OneBook เพิ่มได้**

- กุญแจ API (`X-API-Key`) สำหรับดึงข้อมูลย้อนหลังเอง เผื่อ webhook หลุด
- endpoint อ่านรายการฟอร์ม ผู้ใช้ และคำขอ

**ภาษาและรูปแบบ**

- ข้อมูลทั้งหมดเป็น JSON, UTF-8
- เวลาเป็น **UTC** รูปแบบ ISO 8601 (`2026-09-16T10:50:58.673Z`)
- จำนวนเงินเป็นตัวเลข (number) หน่วยบาท ไม่ใช่สตางค์ ไม่มีเครื่องหมายคั่นหลัก

## 2. ขอบเขต: อะไรต้องไหลจากไหนไปไหน

| เหตุการณ์ | ทิศทาง | ข้อมูลที่ไหล | สถานะ |
|---|---|---|---|
| คำขออนุมัติครบทุกขั้น | เรา → OneBook | ใบคำขอเต็มใบ + ผู้อนุมัติทุกขั้น | **พร้อมใช้** |
| คำขอถูกปฏิเสธ | เรา → OneBook | ใบคำขอ + เหตุผล | **พร้อมใช้** |
| ออกเอกสาร (CN/Invoice/ใบเสร็จ) | เรา → OneBook | เลขเอกสาร + ชนิด | **พร้อมใช้** |
| OneBook ดึงคำขอย้อนหลัง | OneBook → เรา | รายการคำขอตามสถานะ/ช่วงเวลา | **พร้อมใช้** |
| OneBook ตั้งคำขอแทนพนักงาน | OneBook → เรา | สร้างใบคำขอใหม่ | **พร้อมใช้** |
| ไฟล์แนบ (ใบเสนอราคา ใบเสร็จ) | เรา → OneBook | ไฟล์จริง | **พร้อมใช้** |
| บัญชีบันทึก/จ่ายแล้ว แจ้งกลับ | OneBook → เรา | เลขเอกสารบัญชี + วันที่จ่าย | **พร้อมใช้** |
| คำขอถูกยื่น/ยกเลิก/ส่งกลับแก้ | เรา → OneBook | ใบคำขอ | **พร้อมใช้** |

**สิ่งที่อยู่นอกขอบเขตโดยตั้งใจ**

- การอนุมัติผ่าน API — กุญแจ API **ไม่มีสิทธิ์กดอนุมัติแทนคน** การอนุมัติต้องเกิดจากคนจริงในระบบเราเท่านั้น
- การแก้ไขคำขอที่ส่งเข้าสายอนุมัติแล้วจากฝั่ง OneBook
- ข้อมูลส่วนบุคคลที่ไม่จำเป็นต่อบัญชี (เบอร์โทร ลายเซ็น รหัสผ่าน) — ไม่ส่งออกทุกกรณี

## 3. สถาปัตยกรรมการเชื่อม

```
┌─────────────────────────────┐                    ┌──────────────────────────┐
│      Internal-Approve       │                    │         OneBook          │
│                             │                    │                          │
│  พนักงานกรอกฟอร์ม            │                    │                          │
│         ↓                   │   ① ขาออก (push)    │                          │
│  ผู้อนุมัติกดอนุมัติทีละขั้น    │ ─────────────────→ │  POST /hooks/...         │
│         ↓                   │   webhook + HMAC    │  → เข้าคิว → ทำเอกสาร      │
│  อนุมัติครบ → เข้าคิวส่ง       │                    │                          │
│                             │                    │                          │
│  GET /api/v1/requests       │ ←───────────────── │  ② ขาเข้า (pull)          │
│  GET /api/v1/templates      │   X-API-Key         │  job ดึงย้อนหลัง           │
│  POST /api/v1/requests      │                    │                          │
│                             │                    │                          │
│  POST /api/v1/.../accounting│ ←───────────────── │  ③ ทางกลับ (ยังไม่มี)      │
│  (ต้องสร้าง)                 │   X-API-Key         │  แจ้งว่าบันทึก/จ่ายแล้ว     │
└─────────────────────────────┘                    └──────────────────────────┘
```

**ทำไมต้องมีทั้ง push และ pull**

ช่องทาง push (webhook) ให้ข้อมูลถึงเร็วที่สุด แต่ถ้า OneBook ล่มตอนที่เหตุการณ์เกิด
และเรายิงซ้ำครบโควตาแล้ว ข้อมูลใบนั้นจะไม่ถึงปลายทางเลย
ช่องทาง pull จึงเป็นตาข่ายรองรับ — ให้ OneBook ตั้ง job มาดูดของที่ตกหล่นได้เอง
**แนะนำให้ทำทั้งสองทางตั้งแต่แรก** ไม่ใช่ทำ push อย่างเดียวแล้วหวังว่าจะไม่พลาด

## 4. การยืนยันตัวตน

### 4.1 OneBook เรียกเข้ามา → ใช้กุญแจ API

ส่งกุญแจที่ header **`X-API-Key`** ทุกครั้ง

```http
GET /api/v1/requests?status=APPROVED HTTP/1.1
Host: internal-approve.onrender.com
X-API-Key: ia_9f2c4a1b8e7d6c5a4b3e2d1c0f9e8d7c6b5a4f3e2d1c0b9a
```

**คุณสมบัติของกุญแจ**

| | |
|---|---|
| รูปแบบ | `ia_` + เลขฐานสิบหก 48 ตัว |
| ออกที่ไหน | เมนู **ระบบและการเชื่อมต่อ → เชื่อมต่อระบบภายนอก** (เฉพาะผู้ดูแลระบบ) |
| การเก็บ | ระบบเก็บเฉพาะค่าแฮช **ดูย้อนหลังไม่ได้** ต้องคัดลอกตอนสร้างครั้งเดียว |
| สิทธิ์ | `read` อย่างเดียว หรือ `read + write` (write = สร้างคำขอได้) |
| เพิกถอน | กดเพิกถอนได้ทันที ไม่กระทบกุญแจใบอื่น |
| อัตราจำกัด | 120 ครั้ง/นาที ต่อกุญแจหนึ่งใบ (ปรับด้วย `API_RATE_PER_MIN`) |

> **ให้ OneBook ใช้กุญแจของตัวเองหนึ่งใบแยกจากระบบอื่น** เพื่อให้เพิกถอนหรือไล่ดูการใช้งานได้ตรงตัว

**คำตอบเมื่อไม่ผ่าน**

```json
// 401 — กุญแจผิดหรือถูกเพิกถอน
{ "error": "กุญแจไม่ถูกต้องหรือถูกเพิกถอนแล้ว (ส่งมาที่ header X-API-Key)" }

// 403 — กุญแจอ่านอย่างเดียวแต่พยายามเขียน
{ "error": "กุญแจ \"OneBook\" เป็นสิทธิ์อ่านอย่างเดียว" }

// 429 — เรียกถี่เกิน
{ "error": "เรียกถี่เกินกำหนด — ลองใหม่ในอีกหนึ่งนาที" }
```

### 4.2 เรายิงออกไปหา OneBook → ใช้ลายมือชื่อ HMAC

ทุก webhook มี header `X-Signature-256` ที่คำนวณจาก **เนื้อ request ดิบ (raw body)**

```
X-Signature-256: sha256=<hex ของ HMAC-SHA256(WEBHOOK_SECRET, raw_body)>
```

ฝั่ง OneBook ต้องคำนวณเองแล้วเทียบ — **ห้ามเชื่อเพราะมาจาก IP ที่คุ้นเคย**
ถ้าไม่ตรง ให้ตอบ `401` แล้วทิ้ง

> ต้องเทียบกับ **body ดิบ** ก่อนผ่าน JSON parser
> ถ้า parse แล้ว stringify ใหม่ ช่องว่างและลำดับคีย์จะเปลี่ยน ลายมือชื่อจะไม่มีวันตรง

## 5. ขาออก: Webhook (พร้อมใช้แล้ว)

### 5.1 การตั้งค่าฝั่งเรา

ตั้งเป็น environment variable บน Render:

```bash
WEBHOOK_URL=https://onebook.example.com/hooks/internal-approve
WEBHOOK_SECRET=<สุ่มยาวอย่างน้อย 32 ตัวอักษร เก็บเป็นความลับทั้งสองฝั่ง>
WEBHOOK_EVENTS=request.approved,request.rejected,document.issued
```

`WEBHOOK_EVENTS` คือรายการเหตุการณ์ที่ยอมส่ง — เหตุการณ์ที่ไม่อยู่ในรายการจะไม่ถูกเข้าคิวเลย

### 5.2 เหตุการณ์ที่ส่งได้ตอนนี้

| `event` | เกิดเมื่อ | ข้อมูลเพิ่มนอกจาก `request` |
|---|---|---|
| `request.approved` | คำขอผ่านการอนุมัติ **ขั้นสุดท้าย** ครบทุกขั้น | — |
| `request.rejected` | มีผู้อนุมัติคนใดคนหนึ่งกดไม่อนุมัติ | `reason` — เหตุผลที่พิมพ์ไว้ |
| `document.issued` | ผู้ดูแลออกเลขเอกสารให้ใบที่อนุมัติแล้ว | `document` (เลขเอกสาร), `doc_type` |
| `request.submitted` | ยื่นเข้าสายอนุมัติ | — |
| `request.returned` | ถูกส่งกลับให้แก้ | `reason` |
| `request.cancelled` | ผู้จัดทำยกเลิกเอง | `reason` |
| `document.voided` | เลขเอกสารถูกยกเลิก | `document`, `doc_type`, `reason` |

> เหตุการณ์จะถูกส่งก็ต่อเมื่อมีชื่ออยู่ใน `WEBHOOK_EVENTS` — ค่าเริ่มต้นมีแค่สามตัวแรก
> ถ้าต้องการตัวที่เหลือให้เพิ่มชื่อเข้าไปในตัวแปรนั้น

> `request.approved` ยิงเฉพาะตอนจบ **ระดับจริง (FINAL)** เท่านั้น
> การอนุมัติระดับเบื้องต้น (PRELIM) ไม่ยิง เพราะยังไม่ถือว่าจบกระบวนการ

### 5.3 หน้าตาของ request ที่เรายิงไป

```http
POST /hooks/internal-approve HTTP/1.1
Host: onebook.example.com
Content-Type: application/json
X-Signature-256: sha256=7b1f...c9a2

{
  "delivery_id": 184,
  "attempt": 1,
  "event": "request.approved",
  "sent_at": "2026-09-16T11:01:37.884Z",
  "request": { ...ดูข้อ 7... }
}
```

กรณี `request.rejected` จะมีคีย์ `reason` เพิ่มระดับบนสุด
กรณี `document.issued` จะมีคีย์ `document` และ `doc_type` เพิ่มระดับบนสุด

```json
{
  "event": "document.issued",
  "sent_at": "2026-09-16T11:05:00.000Z",
  "request": { "...": "..." },
  "document": "CN-202609-0003",
  "doc_type": "CN"
}
```

### 5.4 กติกาการส่งซ้ำ

| | |
|---|---|
| ถือว่าสำเร็จเมื่อ | ตอบ HTTP `2xx` |
| เวลารอสูงสุด | 15 วินาที เกินนี้ถือว่าไม่สำเร็จ |
| รอบส่งซ้ำ | ทุก 5 นาที |
| จำนวนครั้งสูงสุด | 5 ครั้ง แล้วขึ้นสถานะ `FAILED` ให้ผู้ดูแลเห็น |
| ลำดับ | **ไม่รับประกันลำดับ** ใบที่เกิดทีหลังอาจถึงก่อน |
| ความซ้ำ | **อาจถึงซ้ำได้** ถ้าปลายทางตอบช้าจนเรานับว่าไม่สำเร็จแต่ปลายทางทำงานไปแล้ว |

**ข้อมูลที่ส่งเป็นภาพ ณ ตอนเกิดเหตุการณ์ ไม่ใช่สภาพล่าสุด**

ตัว payload ถูกประกอบและเก็บไว้ตั้งแต่ตอนเข้าคิว ถ้าเอกสารถูกแก้ทีหลัง ข้อความที่ส่งซ้ำ
ยังเป็นเนื้อหาเดิมของจังหวะนั้น — ตั้งใจให้เป็นแบบนี้ เพราะเหตุการณ์ "อนุมัติแล้ว" หมายถึง
สภาพ ณ ตอนอนุมัติ ถ้าต้องการสภาพล่าสุดให้ดึงด้วย `GET /api/v1/requests/{doc_no}` แทน

**สิ่งที่ OneBook ต้องทำเพราะข้อจำกัดข้างบน**

1. **ตอบเร็วก่อน ทำงานทีหลัง** — รับเข้าคิวแล้วตอบ `200` ทันที อย่าทำงานหนักคาไว้ใน request
2. **กันซ้ำด้วยคีย์ที่แน่นอน** — ใช้คู่ `(request.doc_no, event)` เป็นกุญแจเฉพาะในตารางฝั่ง OneBook
   ถ้ามีอยู่แล้วให้ตอบ `200` เฉย ๆ ไม่ต้องสร้างเอกสารซ้ำ
3. **อย่าอิงลำดับ** — ถ้าได้ `document.issued` ก่อน `request.approved` ต้องยังทำงานถูก

> ทุก envelope มี **`delivery_id`** (เลขการส่งครั้งนั้นในคิวของเรา) และ **`attempt`**
> (ครั้งที่เท่าไรของการพยายามส่งใบเดิม) ใช้ `delivery_id` เป็นกุญแจกันซ้ำได้ตรงตัวที่สุด
> และใช้อ้างอิงเวลาสองฝั่งมาเทียบ log กัน

### 5.5 ตัวอย่างโค้ดรับฝั่ง OneBook

**Node.js + Express**

```js
const express = require("express");
const crypto = require("crypto");

const app = express();
const SECRET = process.env.INTERNAL_APPROVE_WEBHOOK_SECRET;

// สำคัญ: ต้องเก็บ body ดิบไว้ ก่อน parse เป็น JSON
app.post(
  "/hooks/internal-approve",
  express.raw({ type: "application/json" }),
  async (req, res) => {
    const given = req.get("X-Signature-256") || "";
    const expected =
      "sha256=" + crypto.createHmac("sha256", SECRET).update(req.body).digest("hex");

    // เทียบแบบเวลาคงที่ กันการเดาทีละตัวอักษร
    const ok =
      given.length === expected.length &&
      crypto.timingSafeEqual(Buffer.from(given), Buffer.from(expected));
    if (!ok) return res.status(401).send("bad signature");

    const payload = JSON.parse(req.body.toString("utf8"));

    // กันซ้ำ: คู่ (doc_no, event) ต้องเป็น unique ในตารางนี้
    const inserted = await db.query(
      `INSERT INTO ia_inbox (doc_no, event, payload, received_at)
       VALUES ($1, $2, $3, now())
       ON CONFLICT (doc_no, event) DO NOTHING
       RETURNING id`,
      [payload.request.doc_no, payload.event, payload],
    );

    // ตอบก่อน แล้วค่อยไปทำเอกสารในคิวเบื้องหลัง
    res.status(200).json({ ok: true });
    if (inserted.rowCount > 0) queue.push(inserted.rows[0].id);
  },
);
```

**PHP (Laravel)**

```php
public function handle(Request $request)
{
    $raw = $request->getContent();
    $expected = 'sha256=' . hash_hmac('sha256', $raw, config('services.internal_approve.secret'));

    if (!hash_equals($expected, $request->header('X-Signature-256', ''))) {
        return response('bad signature', 401);
    }

    $payload = json_decode($raw, true);

    IaInbox::firstOrCreate(
        ['doc_no' => $payload['request']['doc_no'], 'event' => $payload['event']],
        ['payload' => $payload, 'received_at' => now()],
    );

    return response()->json(['ok' => true]);   // ทำเอกสารต่อใน queue job
}
```

### 6.6 `POST /api/v1/requests` — สร้างคำขอจากฝั่ง OneBook

ใช้เมื่อเรื่องตั้งต้นจากฝ่ายบัญชี เช่น บัญชีเป็นคนเปิดเรื่องขอเบิกแทนพนักงาน
**ต้องใช้กุญแจสิทธิ์ `write`**

```bash
curl -X POST https://internal-approve.onrender.com/api/v1/requests \
  -H "X-API-Key: $KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "template": "MPRQ",
    "requester": "somchai@shd-technology.co.th",
    "submit": true,
    "fields": {
      "subject": "ค่าจัดงาน Event สาขารามอินทรา",
      "q_0nimd9": 1
    }
  }'
```

| คีย์ | บังคับ | ความหมาย |
|---|---|---|
| `template` | ✔ | `code` ของฟอร์ม |
| `requester` | ✔ | **อีเมล**ของผู้จัดทำ — สายอนุมัติคิดจากคนนี้ |
| `submit` | — | `true` (ค่าเริ่มต้น) = ส่งเข้าสายอนุมัติทันที, `false` = เก็บเป็นฉบับร่าง |
| `urgent_reason` | — | เหตุผลกรณียื่นกระชั้น |
| `fields` | — | ค่าของแต่ละช่อง คีย์คือ `field_key` |

**สำคัญ:** ทางนี้ **ไม่ใช่ทางลัดข้ามกฎ** — ผ่านตัวสร้างตัวเดียวกับหน้าเว็บ กติกาทุกข้อ
(ช่องบังคับ ชนิดข้อมูล การยื่นล่วงหน้า วงเงินใบหลัก การสร้างสายอนุมัติ) บังคับใช้เหมือนกันหมด

คำตอบสำเร็จ `201` `{ "data": { "...ใบคำขอ..." } }`

คำตอบเมื่อกรอกไม่ครบ `422`:

```json

  "error": "ยังกรอกไม่ครบ 2 ช่อง — ดูรายละเอียดใน fields",
  "fields": { "q_0nimd9": "ต้องกรอก", "q_0nimfc": "ต้องกรอก" }

```

ส่งรหัสช่องที่ฟอร์มไม่มี `400`:

```json

```

## 8. การแมปข้อมูลเข้าระบบบัญชี

### 8.1 ใช้ `role` ไม่ใช่ชื่อช่อง

รหัสช่องในระบบเราเป็นค่าที่สร้างอัตโนมัติ เช่น `q_0nhc3s` — ผู้ดูแลเพิ่มหรือลบช่องได้ตลอด
**อย่าฝังรหัสช่องไว้ในโค้ดฝั่ง OneBook** ให้ใช้ `role` ที่ติดมากับนิยามฟอร์มแทน

| `role` | ความหมาย | ใช้ทำอะไรฝั่งบัญชี |
|---|---|---|
| `TITLE` | หัวเรื่องของเอกสาร | คำอธิบายรายการ |
| `AMOUNT` | วงเงิน | ยอดเงินที่ขอเบิก/ตั้งเจ้าหนี้ |
| `DATE` | วันที่ของเอกสาร | วันที่เอกสาร |
| `EVENT_DATE` | วันที่จัดงาน/วันที่ใช้เงินจริง | วันที่ครบกำหนดจ่าย |
| `PERIODS` | จำนวนงวดที่จะทยอยเบิก | ตั้งงวดจ่าย |

ค่าที่มี `role` จะถูกยกขึ้นมาไว้ระดับบนสุดของ payload ให้แล้ว (`title`, `amount`, `doc_date`)
จึงอ่านตรงนั้นได้เลยโดยไม่ต้องขุดใน `fields`

### 8.2 ⚠️ ข้อจำกัดที่ต้องแก้ก่อนเชื่อมจริง

จากการตรวจข้อมูลจริงวันที่ 20 ก.ย. 2569:

| ฟอร์ม | ตั้ง `AMOUNT` แล้ว? | ผลที่ตามมา |
|---|---|---|
| ใบลดหนี้ (CN) | ✅ | `amount` มีค่าครบทั้ง 13 ใบ |
| Key Account Business agreement | ❌ | 5 จาก 7 ใบ `amount` เป็น `null` |
| Manpower Request | ❌ | ทั้ง 6 ใบ `amount` เป็น `null` |
| Marketing-KOL费用申请单 | ❌ | ทั้ง 5 ใบ `amount` เป็น `null` |
| Vat税金 | ❌ | ทั้ง 5 ใบ `amount` เป็น `null` |

**รวมแล้ว 21 จาก 36 ใบไม่มียอดเงินติดมาด้วย** — ถ้าเชื่อมตอนนี้ OneBook จะได้ใบขออนุมัติ
ที่ไม่รู้ว่าเป็นเงินเท่าไร

**งานที่ต้องทำ (ฝั่ง Internal-Approve):** เข้าเมนู **แม่แบบฟอร์ม** แล้วตั้งบทบาท `AMOUNT`
ให้ช่องจำนวนเงินของทุกฟอร์มที่เกี่ยวกับการเงิน และตั้ง `DATE` / `EVENT_DATE` ตามความเหมาะสม
เป็นการตั้งค่าในหน้าเว็บ ไม่ต้องแก้โค้ด

### 8.3 ตารางแมปที่แนะนำ

| ฝั่ง Internal-Approve | ฝั่ง OneBook |
|---|---|
| `doc_no` | เลขที่อ้างอิงเอกสารต้นเรื่อง (unique) |
| `type.code` | ประเภทเอกสาร/ผังบัญชีที่จะลง |
| `title` | คำอธิบายรายการ |
| `amount` | ยอดรวมก่อนภาษี |

## 9. สิ่งที่ยังไม่มี ต้องสร้างเพิ่ม

ส่วนนี้คือ **รายการงานจริง** ที่ต้องทำก่อนจะเรียกว่าเชื่อมสมบูรณ์
ทุกหัวข้อเขียนสัญญา API ที่เสนอไว้แล้ว ทั้งสองฝั่งเริ่มทำขนานกันได้

### 9.1 ไฟล์แนบ — ✅ ทำเสร็จแล้ว (20 ก.ย. 2569)

payload มีคีย์ `attachments` แล้ว และมี endpoint ดาวน์โหลดที่รับกุญแจ API

```
GET /api/v1/files/{id}
Header: X-API-Key
→ 200 ไฟล์จริง (Content-Disposition: attachment เสมอ)
→ 401 ไม่มีกุญแจ / กุญแจผิด
→ 404 ไม่พบไฟล์แนบหมายเลขนี้
→ 410 แถวยังอยู่ แต่ไฟล์หายจากที่เก็บ
```

```bash
curl -H "X-API-Key: $KEY" https://internal-approve.onrender.com/api/v1/files/9 -o ใบเสนอราคา.pdf
```

แยกจาก `/api/files/{id}` ที่หน้าเว็บใช้โดยตั้งใจ — อันนั้นตรวจสิทธิ์ราย **คน** ว่าผู้ใช้คนนี้
มองเห็นเอกสารใบนี้ไหม ซึ่งไม่มีความหมายกับระบบภายนอกที่ไม่ใช่พนักงานคนใด
การเอากุญแจ API ไปเสียบในด่านเดิมจะกลายเป็นการเจาะรูบนกฎการมองเห็นของทั้งระบบ

### 9.2 เหตุการณ์เพิ่มเติม — ✅ ทำเสร็จแล้ว (20 ก.ย. 2569)

เพิ่ม `request.submitted` · `request.returned` · `request.cancelled` · `document.voided`
ดูรายละเอียดใน [ข้อ 5.2](#52-เหตุการณ์ที่ส่งได้ตอนนี้) — ต้องใส่ชื่อใน `WEBHOOK_EVENTS` ถึงจะถูกส่ง

### 9.3 ทางกลับ: OneBook แจ้งสถานะกลับ — ✅ ทำเสร็จแล้ว (20 ก.ย. 2569)

```
POST /api/v1/requests/{doc_no หรือ id}/accounting
Header: X-API-Key  (ต้องเป็นกุญแจสิทธิ์ write)
Content-Type: application/json
```

```json
{
  "state": "RECORDED",
  "external_ref": "OB-PV-2026-00871",
  "external_url": "https://onebook.example.com/vouchers/871",
  "amount": 45000,
  "occurred_at": "2026-09-17T03:20:00.000Z",
  "note": "ตั้งเจ้าหนี้แล้ว รอรอบจ่าย 25 ก.ย."
}
```

| คีย์ | บังคับ | หมายเหตุ |
|---|---|---|
| `state` | ✔ | `RECEIVED` / `RECORDED` / `PAID` / `REJECTED` |
| `external_ref` | — | เลขเอกสารฝั่งบัญชี — **ใช้เป็นส่วนหนึ่งของกุญแจกันซ้ำ** |
| `external_url` | — | ลิงก์เปิดเอกสารนั้นในระบบบัญชี แสดงบนหน้าเอกสารของเรา |
| `amount` | — | ยอดจริงที่บัญชีบันทึก (อาจต่างจากยอดที่ขอ) |
| `occurred_at` | — | เวลาที่เกิดเหตุจริง ไม่ใส่ = เวลาที่เรียกเข้ามา |
| `note` | เมื่อ `REJECTED` | ตีกลับต้องบอกเหตุผลเสมอ ไม่งั้นตอบ `422` |

**คำตอบ**

```json
// 201 — บันทึกใหม่
{ "created": true, "data": { "id": 4, "state": "RECORDED", "...": "..." } }

// 200 — เคยบันทึกแล้ว (ยิงซ้ำด้วย state + external_ref เดิม)
{ "created": false, "data": { "...": "..." } }
```

**พฤติกรรม**

- เก็บเป็นประวัติทีละแถว ไม่ทับของเดิม — เรื่องหนึ่งเดินได้หลายจังหวะ
- ยิงซ้ำด้วย `state` + `external_ref` เดิม = ไม่เกิดแถวซ้ำ (บังคับด้วย unique index ในฐานข้อมูล)
- แสดงบนหน้ารายละเอียดเอกสารเป็นการ์ด **"ความคืบหน้าฝั่งบัญชี"** พร้อมลิงก์และชื่อระบบต้นทาง
- `PAID` และ `REJECTED` จะแจ้งเตือนผู้จัดทำทันที (ผ่าน Lark/ช่องทางที่ตั้งไว้)
- บันทึกลงประวัติการดำเนินการของเอกสารด้วย ตามรอยย้อนหลังได้ว่าใครแจ้งอะไรเมื่อไหร่

### 9.4 การจับคู่เอกสารสองระบบ

เพิ่มช่อง `external_ref` บนใบคำขอ เพื่อให้เปิดจากฝั่งเราแล้วกระโดดไปดูเอกสารใน OneBook ได้
และกันการลงบัญชีซ้ำ — ถ้าใบไหนมี `external_ref` แล้ว OneBook ควรถือว่าเคยทำแล้ว

### 9.5 เลขอ้างอิงของการส่งแต่ละครั้ง — ✅ ทำเสร็จแล้ว (20 ก.ย. 2569)

envelope มี `delivery_id` และ `attempt` แล้ว ดู [ข้อ 5.3](#53-หน้าตาของ-request-ที่เรายิงไป)

### 9.6 สรุปงานและผู้รับผิดชอบ

| # | งาน | ฝั่ง | สถานะ |
|---|---|---|---|
| 1 | ตั้ง `AMOUNT`/`DATE` ให้ทุกฟอร์มการเงิน | Internal-Approve (ตั้งค่าในหน้าเว็บ) | **ยังไม่ได้ทำ — ต้องทำก่อนเชื่อมจริง** |
| 2 | endpoint รับ webhook + ตรวจลายมือชื่อ | OneBook | รอฝั่ง OneBook |
| 3 | ตารางกันซ้ำฝั่ง OneBook | OneBook | รอฝั่ง OneBook |
| 4 | `attachments` ใน payload + `/api/v1/files/{id}` | Internal-Approve | ✅ เสร็จ 20 ก.ย. 2569 |
| 5 | `POST /api/v1/requests/{doc_no}/accounting` | Internal-Approve | ✅ เสร็จ 20 ก.ย. 2569 |
| 6 | job ดึงย้อนหลัง | OneBook | รอฝั่ง OneBook |
| 7 | เหตุการณ์เพิ่ม (`submitted`, `returned`, `cancelled`, `voided`) | Internal-Approve | ✅ เสร็จ 20 ก.ย. 2569 |
| 8 | `delivery_id` ใน envelope | Internal-Approve | ✅ เสร็จ 20 ก.ย. 2569 |
| 9 | ตั้งแผนกให้ผู้ใช้ | Internal-Approve (ตั้งค่าในหน้าเว็บ) | ยังไม่ได้ทำ |

**สรุป: งานฝั่ง Internal-Approve ที่ต้องเขียนโค้ดเสร็จหมดแล้ว** เหลือเฉพาะการตั้งค่าในหน้าเว็บ
(ข้อ 1 และ 9) กับงานฝั่ง OneBook

## 12. การตั้งค่าและการทดสอบ

### 12.1 ตัวแปรที่ต้องตั้ง (ฝั่ง Internal-Approve, บน Render)

```bash
WEBHOOK_URL=https://onebook.example.com/hooks/internal-approve
WEBHOOK_SECRET=<ความลับร่วม อย่างน้อย 32 ตัวอักษร>
WEBHOOK_EVENTS=request.approved,request.rejected,document.issued
API_RATE_PER_MIN=120        # ไม่ตั้งก็ได้ ค่าเริ่มต้น 120
```

### 12.2 ขั้นตอนทดสอบที่แนะนำ

1. **ทดสอบขาออกโดยยังไม่ต้องมี OneBook** — ตั้ง `WEBHOOK_URL` ไปที่ `https://webhook.site/<id>`
   แล้วลองอนุมัติเอกสารทดสอบหนึ่งใบ ดูว่า payload หน้าตาตรงกับเอกสารนี้
2. **ทดสอบลายมือชื่อ** — เอา raw body จาก webhook.site มาคำนวณ HMAC ด้วย secret เดียวกัน
   เทียบกับ header ที่ได้รับ ต้องตรงกัน
3. **ทดสอบขาเข้า** — `curl` ตาม [ข้อ 6](#6-ขาเข้า-rest-api-พร้อมใช้แล้ว) ด้วยกุญแจ read
4. **ทดสอบการกันซ้ำ** — ยิง payload เดิมเข้า OneBook สองครั้ง ต้องได้เอกสารบัญชีใบเดียว
5. **ทดสอบกรณีล้มเหลว** — ปิด endpoint ฝั่ง OneBook ชั่วคราว อนุมัติเอกสาร แล้วเปิดใหม่
   ภายใน 25 นาที ต้องได้รับข้อมูลครบโดยไม่ต้องทำอะไร

### 12.3 ปุ่มทดสอบในหน้าผู้ดูแล

เมนู **ระบบและการเชื่อมต่อ → เชื่อมต่อระบบภายนอก** มีปุ่ม **"ส่งข้อความทดสอบ"**
ยิงไปที่ `WEBHOOK_URL` ทันทีพร้อมลายมือชื่อจริง แล้วบอกผลว่าปลายทางตอบอะไร

```json
{ "event": "ping", "test": true, "sent_at": "...", "request": { "...ใบล่าสุดเป็นตัวอย่าง..." } }
```

ใช้ตรวจว่า URL ถูก ความลับตรงกัน และปลายทางรับได้ **ก่อน**จะมีเอกสารจริงวิ่งผ่าน
ไม่ต้องรออนุมัติเอกสารจริงแล้วลุ้น

> ⚠️ ฝั่ง OneBook **ต้องไม่เอา `event: "ping"` ไปสร้างเอกสารบัญชี** ให้ตรวจ `test === true`
> หรือ `event === "ping"` แล้วตอบ `200` เฉย ๆ

### 12.4 หน้าติดตามสถานะฝั่งเรา

เมนู **ระบบและการเชื่อมต่อ → เชื่อมต่อระบบภายนอก** แสดง:

- URL ปลายทางที่ตั้งไว้ และมีการตั้ง secret หรือไม่
- รายการส่ง 25 ครั้งล่าสุด พร้อมสถานะ (`PENDING` / `SENT` / `FAILED` / `SKIPPED`),
  จำนวนครั้งที่ลอง, รหัส HTTP ที่ได้, ข้อความผิดพลาด
- สรุปจำนวนแยกตามสถานะ

รายการที่ขึ้นสถานะ `FAILED` (ลองครบ 5 ครั้งแล้วไม่ผ่าน) มีปุ่ม **"ส่งซ้ำ"** ให้สั่งใหม่ได้
หลังปลายทางแก้ปัญหาเสร็จ — นับครั้งใหม่ตั้งแต่ต้น ไม่ต้องยอมให้ข้อมูลใบนั้นหายไป

ใช้หน้านี้เป็นจุดแรกเวลาสองฝั่งเถียงกันว่า "ส่งแล้ว" หรือ "ไม่ได้รับ"

| เฟส | ขอบเขต | สถานะ | เกณฑ์ว่าเสร็จ |
|---|---|---|---|
| **1 — เตรียมข้อมูล** | ตั้ง `AMOUNT`/`DATE` ให้ทุกฟอร์มการเงิน · ตั้งแผนกให้ผู้ใช้ · ออกกุญแจ API ให้ OneBook | **ค้างอยู่** | `GET /api/v1/requests?status=APPROVED` คืนใบที่มี `amount` ครบทุกใบ |
| **2 — ขาออกทางเดียว** | OneBook เปิด endpoint รับ webhook + ตรวจลายมือชื่อ + ตารางกันซ้ำ | รอ OneBook | อนุมัติเอกสารจริงหนึ่งใบแล้วเกิดเอกสารบัญชีอัตโนมัติ |
| **3 — ไฟล์แนบและตาข่ายรองรับ** | ฝั่งเรา: `attachments` + `/api/v1/files/{id}` · ฝั่ง OneBook: job ดึงย้อนหลัง | **ฝั่งเราเสร็จแล้ว** | ปิด endpoint ฝั่ง OneBook 1 ชั่วโมงแล้วข้อมูลยังครบหลังเปิดใหม่ |
| **4 — ทางกลับ** | `POST .../accounting` · การ์ดสถานะบนหน้าเอกสาร · เหตุการณ์เพิ่มเติม | **ฝั่งเราเสร็จแล้ว** | ผู้จัดทำเห็นสถานะ "จ่ายแล้ว" ในระบบเราโดยไม่ต้องถามบัญชี |

## 14. ภาคผนวก

### 14.1 สถานะคำขอ

| ค่า | ความหมาย | บัญชีควรทำอะไร |
|---|---|---|
| `DRAFT` | ฉบับร่าง ยังไม่ยื่น | ไม่ต้องทำอะไร (ไม่ส่งออกอยู่แล้ว) |
| `PENDING` | รออนุมัติ | เห็นไว้เฉย ๆ ยังไม่ลงบัญชี |
| `PRELIM_APPROVED` | อนุมัติเบื้องต้นแล้ว รอระดับจริง | ยังไม่ลงบัญชี |
| `APPROVED` | **อนุมัติครบทุกขั้น** | ลงบัญชีได้ |
| `REJECTED` | ไม่อนุมัติ | ถ้าตั้งเรื่องไว้แล้วต้องยกเลิก |
| `RETURNED` | ถูกส่งกลับให้แก้ | รอใบแก้ไข |
| `CANCELLED` | ผู้จัดทำยกเลิก | ถ้าตั้งเรื่องไว้แล้วต้องยกเลิก |

### 14.2 ชนิดช่องกรอก

`TEXT` `TEXTAREA` `NUMBER` `MONEY` `DATE` `DATERANGE` `SELECT` `DROPDOWN` `MULTISELECT`
`USER` `FILE` `IMAGE` `TABLE` `TOTAL` `REQUEST` `HEADING`

> `HEADING` เป็นหัวข้อคั่น ไม่มีค่าใน `fields` และไม่ถูกส่งออกมาใน `/api/v1/templates`

### 14.3 ชนิดเอกสารที่ออกได้

| `doc_type` | คำนำหน้าเลข (ค่าเริ่มต้น) | ความหมาย |
|---|---|---|
| `INVOICE` | `INV` | ใบแจ้งหนี้ |
| `CN` | `CN` | ใบลดหนี้ |
| `DN` | `DN` | ใบเพิ่มหนี้ |
| `RECEIPT` | `RC` | ใบเสร็จรับเงิน |
| `OTHER` | `DOC` | อื่น ๆ |

รูปแบบเลข: `{คำนำหน้า}-{ปีเดือน}-{ลำดับ 4 หลัก}` เช่น `CN-202609-0003`
เลขเดินแยกกันต่อชนิดต่อเดือน และ **ไม่ถูกนำกลับมาใช้ซ้ำแม้เอกสารถูกยกเลิก**

### 14.4 รหัสข้อผิดพลาด

| HTTP | ความหมาย | ฝั่ง OneBook ควรทำ |
|---|---|---|
| `400` | รูปแบบคำขอผิด (JSON เสีย, ส่งช่องที่ไม่มี) | แก้โค้ด ไม่ต้องลองซ้ำ |
| `401` | กุญแจผิด/ถูกเพิกถอน | แจ้งผู้ดูแล ไม่ต้องลองซ้ำ |
| `403` | กุญแจไม่มีสิทธิ์เขียน | ขอกุญแจใหม่ |
| `404` | ไม่พบเอกสาร/ฟอร์ม/ผู้ใช้ | ตรวจค่าที่ส่ง |
| `422` | ข้อมูลไม่ผ่านกติกาของฟอร์ม | ดูรายละเอียดใน `fields` |
| `429` | เรียกถี่เกิน | รอ 1 นาทีแล้วลองใหม่ |
| `5xx` | ฝั่งเรามีปัญหา | ลองซ้ำแบบถอยหลังเพิ่มระยะ |

### 14.5 เลขที่เอกสารของคำขอ

```
AP-MPRQ-202609-0001
│  │    │      └── ลำดับ 4 หลัก เดินแยกต่อฟอร์มต่อเดือน
│  │    └───────── ปีเดือน (ค.ศ.)
│  └────────────── ตัวย่อฟอร์ม (ตั้งได้ที่หน้าแม่แบบฟอร์ม)
└───────────────── คงที่เสมอ
```

- ไม่ซ้ำทั้งระบบ (บังคับด้วย unique constraint ในฐานข้อมูล)
- ปลอดภัยเมื่อหลายคนกดพร้อมกัน — เดินเลขด้วยตัวนับกลางในฐานข้อมูล
- เอกสารเก่าก่อนเปลี่ยนรูปแบบเป็นเลขล้วน เช่น `202608200001` ยังมีอยู่ในระบบ
  **ฝั่ง OneBook ต้องรับได้ทั้งสองรูปแบบ** อย่า validate ด้วย regex ที่รับเฉพาะรูปแบบใหม่
