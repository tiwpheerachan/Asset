## 1. ระบบนี้คืออะไร

One OA คือระบบยื่นคำขอและอนุมัติเอกสารภายในองค์กร เช่น ขออนุมัติส่วนลด ค่าใช้จ่ายการตลาด เบิกจ่าย จัดซื้อ ใบลดหนี้ ค่าใช้จ่ายประจำวัน/สาขา ฯลฯ รองรับสายอนุมัติหลายชั้นตามตำแหน่งงานและวงเงิน คำขอที่อนุมัติแล้วส่งต่อให้ระบบบัญชี/ทรัพย์สินผ่าน webhook/REST ได้

## 2. เข้าใช้งาน บทบาท และตำแหน่งงาน

เข้าสู่ระบบด้วยอีเมล+รหัสผ่าน (`/login`) หรือปุ่ม SSO (ระบบกลาง OIDC) ถ้าเปิดใช้ · มีบังคับเปลี่ยนรหัสครั้งแรก (`/change-password`)

### บทบาท (Role) — คุมสิ่งที่ "เห็น" และสิทธิ์จัดการ
| บทบาท | เห็นอะไร |
|---|---|
| **ADMIN** ผู้ดูแลระบบ | เห็นและจัดการได้ทุกอย่าง |
| **MANAGER** หัวหน้าทีม | เห็นเอกสารทุกฉบับของคนในแผนกตัวเอง |
| **USER** ผู้ใช้ทั่วไป | เห็นเฉพาะเอกสารที่ตนจัดทำ อยู่ในสายอนุมัติ หรือถูกสำเนาถึง |

เพิ่มเติม: ธง **ตรวจสอบได้ (can_audit)** = เห็นทุกคำขอเพื่อสอบทาน แต่อนุมัติ/แก้ไม่ได้

### ตำแหน่งงาน (JobRole) — ใช้กำหนดสายอนุมัติ (คนละอย่างกับ Role)
NONE, **SALES** ผู้แทนขาย, **SALES_MANAGER** ผู้จัดการฝ่ายขาย, **PURCHASING** ฝ่ายจัดซื้อ, **MARKETING** ฝ่ายการตลาด, **FINANCE** ฝ่ายบัญชี/การเงิน, **FINANCE_MANAGER** ผู้จัดการฝ่ายบัญชี, **MD** กรรมการผู้จัดการ

## 3. ภาพรวมเมนู

**ของฉัน**
- แดชบอร์ด (`/dashboard`) — ศูนย์รวมภาพรวมงานอนุมัติ ปรับตามบทบาทผู้ใช้ (ดูหัวข้อ 3.1)
- ส่งคำขอ (`/`) — เลือกฟอร์มเพื่อยื่นคำขอ (จัดกลุ่มตามหมวด + ค้นหา)
- รอฉันอนุมัติ (`/requests?tab=awaiting`) — คำขอที่ค้างที่ขั้นของฉัน (ป้ายตัวเลขข้างเมนู)
- คำขอของฉัน (`/requests?tab=mine`) — คำขอที่ฉันเป็นผู้จัดทำ

**คำขอ**
- ศูนย์การอนุมัติ (`/requests`) — รวมทุกคำขอที่มีสิทธิ์เห็น มีแท็บ ทั้งหมด/รอฉันอนุมัติ/ฉันเป็นผู้จัดทำ/ทีมของฉัน/รอเคลียร์ OA + ตัวกรองสถานะ/ฟอร์ม/คำค้น/วันที่
- ตารางรวมเอกสาร (`/requests/table`) — ตารางแน่นไว้กวาดตาและส่งออก

**ดูแลระบบ** (เฉพาะ ADMIN)
- แม่แบบฟอร์ม (`/admin/forms`) — สร้าง/แก้ฟอร์มและสายอนุมัติ
- วิเคราะห์ประสิทธิภาพ (`/admin/analytics`) — จำนวนคำขอ อัตราอนุมัติ เวลาเฉลี่ยรายผู้อนุมัติ
- เตือนงานค้าง (`/admin/reminders`) — ตั้งค่าการเตือนงานค้าง
- เชื่อมต่อระบบภายนอก (`/admin/api`) — webhook + API key
- สำรองข้อมูล (`/admin/backup`)
- ระบบกลาง SSO (`/admin/sso`) — ตั้งค่า OIDC

อื่น ๆ: รายละเอียดคำขอ (`/requests/[id]`), โปรไฟล์/ลายเซ็น/มอบหมายอนุมัติแทน (`/profile`), คู่มือ (`/help`)

### 3.1 แดชบอร์ด (`/dashboard`)

ศูนย์บัญชาการงานอนุมัติ รวมสิ่งที่ต้องทำ ตัวเลขสำคัญ และกราฟไว้ในหน้าเดียว **ข้อมูลทั้งหมดถูกจำกัดตามสิทธิ์ของผู้ใช้** (ADMIN/ผู้ตรวจสอบเห็นทั้งองค์กร, ผู้จัดการเห็นแผนกตนเอง + งานในสายอนุมัติ, ผู้ใช้ทั่วไปเห็นเฉพาะคำขอของตนเองและที่ตนอยู่ในสาย) — มุมบนขวาบอกช่วงเวลา (เดือนปัจจุบัน) และหัวข้อบอก "มุมมอง" ที่กำลังดู

- **ต้องจัดการตอนนี้** — การ์ดลัด 6 ใบ: รอคุณอนุมัติ, ใกล้เกิน SLA, เกิน SLA, ถูกส่งกลับให้แก้, รอเคลียร์เอกสาร, เลยกำหนดเคลียร์ — คลิกแต่ละใบเพื่อไปยังรายการที่กรองไว้แล้ว
- **ตัวชี้วัด (KPI)** — คำขอทั้งหมด (เทียบเดือนก่อน), มูลค่าที่อนุมัติแล้ว, มูลค่าที่รออนุมัติ, อัตราอนุมัติ, เวลาอนุมัติเฉลี่ย, จำนวนเกิน SLA
- **Funnel** — ขั้นของงานอนุมัติ: ส่งคำขอ → เข้าสู่การอนุมัติ → อนุมัติแล้ว → ส่งบัญชี/ดำเนินการ → เสร็จสิ้น (พร้อม % แปลงจากต้นทาง)
- **กราฟ** — แนวโน้มคำขอรายวัน, สัดส่วนตามประเภทฟอร์ม, มูลค่าแยกตามแผนก, มูลค่ารายเดือน, สถานะ SLA + อายุงานค้างอนุมัติ
- **ตาราง** — งานรอฉันอนุมัติ (จัดลำดับความสำคัญตาม SLA) และคำขอล่าสุด

> ตัวเลขทุกตัวคำนวณจากข้อมูลจริงในระบบ ไม่มีค่าสมมติ หากข้อมูลไม่พอสำหรับบางกราฟจะขึ้นข้อความแจ้งแทน

## 4. วงจรคำขอและสถานะ

### สถานะคำขอ (RequestStatus)
| สถานะ | ความหมาย |
|---|---|
| DRAFT | ฉบับร่าง |
| PENDING | รออนุมัติ |
| PRELIM_APPROVED | อนุมัติเบื้องต้นแล้ว (รอยื่นวงเงินจริง) |
| APPROVED | อนุมัติแล้ว |
| REJECTED | ไม่อนุมัติ |
| RETURNED | ถูกส่งกลับให้แก้ |
| CANCELLED | ยกเลิก |

### ขั้นอนุมัติ (Stage)
- **PRELIM** อนุมัติเบื้องต้น (ขออนุมัติหลักการก่อนรู้ยอดจริง — ถ้าฟอร์มตั้งไว้)
- **FINAL** อนุมัติจริง (ยื่นวงเงินจริง วิ่งสายอนุมัติตามเกณฑ์วงเงิน)

### สถานะผู้อนุมัติแต่ละราย
รอพิจารณา (PENDING), อนุมัติแล้ว (APPROVED), ไม่อนุมัติ (REJECTED), ไม่ต้องพิจารณาแล้ว (SKIPPED), แจ้งให้ทราบ (NOTIFIED = ขั้นสำเนาถึง)

### ไหลของเอกสาร
```
DRAFT ──ส่งคำขอ──> PENDING ──(อนุมัติครบทุกขั้น)──> APPROVED
  │                   │
  │                   ├─ ไม่อนุมัติ ──> REJECTED
  │                   ├─ ส่งกลับให้แก้ ──> RETURNED ──แก้แล้วส่งใหม่──> PENDING
  │                   └─ ดึงกลับ/ยกเลิก ──> DRAFT / CANCELLED
  └─ (ถ้าฟอร์มมีขั้นเบื้องต้น) ส่ง──> PENDING(PRELIM) ──ครบ──> PRELIM_APPROVED ──ยื่นจริง──> PENDING(FINAL)
```

## 5. วิธีใช้งานสำหรับผู้จัดทำ

1. เมนู **ส่งคำขอ** เลือกฟอร์ม → กรอกข้อมูล (ระบบบันทึกร่างอัตโนมัติ)
2. **แนบไฟล์** ได้ทั้งระดับเอกสารและในแต่ละแถวตาราง (ไฟล์ละไม่เกิน 10 MB)
3. กด **ส่งคำขอ** → เข้าสายอนุมัติ ดูความคืบหน้าได้ที่แท็บ "บันทึกการอนุมัติ"
4. ถ้าถูก **ส่งกลับให้แก้ (RETURNED)** → แก้แล้วกด "ส่งอีกครั้ง"
5. ถ้าผ่าน **อนุมัติเบื้องต้น** → กด "ยื่นอนุมัติจริง" ใส่วงเงินจริง (วงเงินนี้กำหนดว่าต้องผ่านใครบ้าง)
6. **ดึงกลับมาแก้ไข** ได้เฉพาะตอน PENDING และยังไม่มีใครในขั้นปัจจุบันกดตัดสิน
7. **ยกเลิกเอกสาร** ได้ก่อนอนุมัติ (อนุมัติแล้วยกเลิกไม่ได้ — ต้องให้ ADMIN ทำ "ยกเลิกเอกสารที่อนุมัติแล้ว" พร้อมเหตุผล)

เครื่องมือเพิ่มเติมในหน้าคำขอ: คัดลอกลิงก์, พิมพ์/PDF, ความคิดเห็น (แนบไฟล์ได้)

## 6. วิธีใช้งานสำหรับผู้อนุมัติ

เปิดคำขอจาก **รอฉันอนุมัติ** หรือกดตัดสินแบบเร็วในรายการ ปุ่มที่มี:
- **✓ อนุมัติ** — ใส่ความคิดเห็นได้ (ไม่บังคับ)
- **✕ ไม่อนุมัติ** — **ต้องใส่เหตุผล**
- **↩ ส่งกลับให้แก้** — คืนให้ผู้จัดทำแก้โดยไม่ปิดเอกสาร (ต้องมีเหตุผล)
- **→ ถ่ายโอน** — ส่งงานในคิวให้คนอื่นพิจารณาแทน
- **+ เพิ่มผู้อนุมัติ** — แทรกผู้อนุมัติก่อน/หลังขั้นของฉัน (เลือกจากตำแหน่งงาน/ผู้ใช้/ไดเรกทอรีด้วยอีเมล)
- **แนบไฟล์/รูป** — แนบหลักฐานพร้อมการตัดสิน

**อนุมัติแทน (รับแทน)**: ถ้ามีการมอบหมาย จะกดอนุมัติแทนเจ้าของคิวได้ในช่วงวันที่กำหนด ระบบบันทึกว่า "(อนุมัติแทน …)" · เจ้าของคิวที่ลา ระบบจะส่งการแจ้งเตือนไปหาผู้รับแทนให้เอง · ห้ามใช้สิทธิ์รับแทนอนุมัติเอกสารของตัวเอง

## 7. สายอนุมัติทำงานอย่างไร

สายอนุมัติกำหนดในแม่แบบฟอร์ม (flow nodes) เป็น **ขั้น (step) เรียงลำดับ** แต่ละขั้นมีสมาชิกและโหมด:
- **ที่มาของผู้อนุมัติ**: ตามตำแหน่งงาน (JOB_ROLE เช่น "ผู้จัดการฝ่ายบัญชี") หรือระบุตัวบุคคล (USER)
- **ขอบเขต**: ในแผนกของผู้ขอ (DEPT) หรือใครก็ได้ที่ถือตำแหน่งนั้น (ANY)
- **โหมดขั้น**: คนเดียว (SEQUENTIAL) / ใครก็ได้ 1 คน (ANY) / ต้องครบทุกคน (ALL)
- **ชนิดโหนด**: ต้องอนุมัติ (APPROVE) หรือสำเนาถึง (CC — แค่แจ้งให้ทราบ ไม่บล็อก)
- **เงื่อนไขวงเงิน**: เช่น ตั้งแต่ 100,000 ขึ้นไปจึงเพิ่มขั้นผู้จัดการฝ่ายบัญชี/กรรมการผู้จัดการ

ระบบตัดคนที่อนุมัติไปแล้วในขั้นก่อนออก ขั้นที่ไม่มีผู้อนุมัติที่เข้าเกณฑ์จะถูกข้าม และถ้าไม่มีใครถือตำแหน่งที่ตั้งไว้จะเตือน "ยังไม่มีผู้ใช้งานที่ถือตำแหน่ง: …" · หน้า "บันทึกการอนุมัติ" และพรีวิวในฟอร์มใช้ตรรกะเดียวกันเป๊ะ จึงเห็นสายอนุมัติจริงล่วงหน้าได้

ตัวอย่างเกณฑ์วงเงิน (ค่าเริ่มต้น): ส่วนลด +ผจก.บัญชี ≥100,000 / +MD ≥500,000 · จัดซื้อ +ผจก.บัญชี ≥50,000 / +MD ≥300,000 · เบิกจ่าย +ผจก.บัญชี ≥20,000 / +MD ≥100,000

## 8. ฟอร์มและแม่แบบ

### ฟอร์มมาตรฐาน
ฟอร์มที่เห็นในระบบจริง (ตามหมวด):
- **งานขาย**: ส่วนลด/ราคาพิเศษ (DISCOUNT), ค่าใช้จ่ายการตลาด (MARKETING)
- **การเงิน**: เบิกจ่าย (REIMBURSE), ใบลดหนี้ CN (CREDIT_NOTE), ค่าใช้จ่ายประจำวัน/日常费用 (DAILY_EXPENSE), ค่าใช้จ่ายสาขา/门店费用 (BRANCH_COST)
- **จัดซื้อ/คลัง**: จัดซื้อ (PURCHASE), เรียกคืนสินค้าเดโม (DEMO_RETURN)
- **ทั่วไป**: บันทึกข้อความทั่วไป (OTHER)

> หมายเหตุ: ชุดเริ่มต้น (seed) มี 7 ฟอร์ม ส่วน DAILY_EXPENSE และ BRANCH_COST เป็นฟอร์มที่เพิ่มเข้ามาในฐานข้อมูลจริง (รายละเอียดสองฟอร์มนี้ดูที่ `OA_Forms_DailyExpense_BranchCost.md`)

### ชนิดฟิลด์ (FieldType)
ข้อความบรรทัดเดียว, ข้อความยาว, ตัวเลข, จำนวนเงิน, วันที่, ตัวเลือก(เลือก 1), ดรอปดาวน์, เลือกหลายค่า, เลือกบุคคล, ไฟล์, รูปภาพ, **ตารางรายการ (TABLE)**, อ้างอิงคำขอที่อนุมัติแล้ว, หัวข้อคั่น, ช่วงเวลา, **ยอดรวมจากตาราง (TOTAL)**

### บทบาทฟิลด์พิเศษ (FieldRole) — มีได้อย่างละ 1 ต่อฟอร์ม
- **TITLE** หัวเรื่องเอกสาร
- **AMOUNT** วงเงิน (ใช้ตัดสินสายอนุมัติ — ต้องเป็นฟิลด์เงิน/ตัวเลข/ยอดรวม)
- **DATE** วันที่เอกสาร
- **EVENT_DATE** วันที่จัดงาน/ใช้เงิน (ใช้คำนวณยื่นล่วงหน้า และกำหนดเคลียร์ OA)
- **PERIODS** จำนวนงวดที่จะทยอยเบิก

ฟอร์มที่มี **ตารางรายการ** ใช้คู่กับฟิลด์ **ยอดรวม** (รวมคอลัมน์เงินให้อัตโนมัติ และตั้งเป็น AMOUNT ได้) · ฟิลด์ซ่อน/แสดงตามเงื่อนไขได้ (แสดงเมื่อฟิลด์ก่อนหน้ามีค่าที่กำหนด)

### เลขที่เอกสาร
รูปแบบ `AP-{prefix}-{YYYYMM}-{ลำดับ4หลัก}` เช่น `AP-DEX-202610-0007` · prefix มาจากค่า `doc_prefix` ที่แอดมินตั้งในฟอร์ม ถ้าไม่ตั้งจะใช้ 4 ตัวแรกของรหัสฟอร์ม · นับแยกตามฟอร์ม+งวด

## 9. การเคลียร์ค่าใช้จ่ายใน OA

หลักการ: One OA "อนุมัติก่อน แล้วค่อยไปตั้งเบิกจริงในระบบ OA/ERP ภายหลัง โดยอ้างเลขอนุมัตินี้" การเคลียร์คือการติดตามว่าตั้งเบิกจริงแล้วหรือยัง
- ตั้งต่อฟอร์ม: **ต้องเคลียร์ภายในกี่วันหลังอนุมัติ** (0 = ไม่ติดตาม)
- กำหนดเคลียร์คิดจาก EVENT_DATE (ถ้าอยู่หลังวันอนุมัติ) หรือวันอนุมัติ + จำนวนวัน
- สถานะ: ไม่ติดตาม / เคลียร์แล้ว (มีเลขอ้างอิง OA) / เหลืออีก N วัน / เลยกำหนด
- ผู้จัดทำบันทึก "เลขที่เอกสารใน OA" เพื่อปิดการเคลียร์ · ระบบเตือนล่วงหน้า ≤3 วันและเมื่อเลยกำหนด (วันละครั้ง)
- ดูได้ที่แท็บ "รอเคลียร์ OA" และวิดเจ็ตหน้าแรก

## 10. งานผู้ดูแลระบบ

- **แม่แบบฟอร์ม**: สร้าง/แก้ฟอร์ม (รหัส ชื่อ หมวด ไอคอน สี doc_prefix), เพิ่ม/เรียง/คัดลอกฟิลด์, จัดการคอลัมน์ตาราง, ตั้งสายอนุมัติ (โหนด/สมาชิก/เงื่อนไข — โหนดใหม่บังคับเป็นขั้น FINAL), ตั้งเวลายื่นล่วงหน้า (lead time แบบเตือน/บล็อก) และโหมดลายเซ็น
- **ผู้ใช้/แผนก**: บทบาท (ADMIN/MANAGER/USER), ตำแหน่งงาน, หัวหน้า, แผนก, ออกรหัสผ่านชั่วคราว (ถ้าระบบกลางคุมบทบาท การแก้บทบาทในเครื่องจะถูกปิด)
- **มอบหมายอนุมัติแทน**: ผู้ใช้ตั้งเองหรือแอดมินตั้งให้ มีช่วงวันที่+เหตุผล ตรวจทับซ้อน/วนซ้ำ
- **เตือนงานค้าง**: ตั้งผ่าน env (เตือนหลัง N วัน, เร่งหลัง N วัน, ข้ามวันหยุด, ช่วงเวลาส่ง) กด sweep เองได้
- **สำรองข้อมูล**: dump + ย้ายไฟล์แนบขึ้น object storage, ดาวน์โหลดได้
- **ออกเอกสาร**: ออกใบ INVOICE/CN/DN/RECEIPT จากคำขอที่อนุมัติแล้ว (นับเลขรายเดือน) ยกเลิกได้ (ADMIN) และยิง webhook `document.issued`

## 11. การเชื่อมต่อระบบภายนอก

### Webhook ขาออก
ตั้ง `WEBHOOK_URL`, `WEBHOOK_SECRET` (เซ็น HMAC `X-Signature-256`), `WEBHOOK_EVENTS` · เหตุการณ์: `request.submitted`, `request.approved`, `request.rejected`, `request.returned`, `request.cancelled`, `document.issued` (ยิงเฉพาะที่ตั้งไว้) มีคิวส่งซ้ำ ≤5 ครั้ง + ปุ่มทดสอบ/ส่งซ้ำ · payload เป็นรูปแบบกลาง (รวมสายอนุมัติ เอกสารที่ออก ไฟล์แนบ)

### REST API ขาเข้า (`/api/v1/*`)
ยืนยันด้วย `X-API-Key` (คีย์ขึ้นต้น `ia_`, สิทธิ์อ่าน/เขียน, จำกัดอัตราเรียก) · endpoints: `GET/POST /requests`, `GET /requests/{id|doc_no}`, `POST /requests/{id}/accounting` (รับสถานะจากบัญชี: รับเรื่อง/บันทึกบัญชี/จ่ายเงิน/ตีกลับ), `GET /templates`, `GET /users`, `GET /ping`
> หมายเหตุความปลอดภัย: **การอนุมัติทำผ่าน API ไม่ได้โดยตั้งใจ** ต้องทำในระบบ (เว็บ หรือการ์ด Lark)

### SSO (ระบบกลาง OIDC)
ตั้ง `SSO_ISSUER`, `SSO_CLIENT_ID/SECRET`, `APP_BASE_URL`, map กลุ่ม→แผนก และตำแหน่ง→บทบาทได้ · redirect = `{baseUrl}/api/auth/sso/callback` · ล็อกเอาท์จบ session ที่ระบบกลางด้วย

### การตัดสินใจด้านความปลอดภัย/สิทธิ์
- การมองเห็นคำขอ: USER = ของตน + อยู่ในสาย + ถูกสำเนาถึง · MANAGER = ทั้งแผนก · ADMIN/ผู้ตรวจสอบ = ทั้งหมด
